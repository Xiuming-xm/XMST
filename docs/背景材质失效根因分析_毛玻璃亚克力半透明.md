# XMST 插件「毛玻璃 / 亚克力 / 半透明」失效根因分析

分析对象：`F:\XMST`（Rust + eframe 0.29.1 + egui 0.29.1 + glow/OpenGL）与其插件
`dist\data\plugins\xmst-frosted-glass-demo.zip`（`manifest.json` + `main.rhai`）。

分析日期：2026-09-29。方法：源码静态取证 + 依赖源码（winit/glutin/eframe/egui）核对 + 实机落盘状态取证。
**本次未做运行时注入，因此「DWM 亚克力在真机上到底有没有模糊」标注为待验证项（§5.C3）。**

> **状态说明**：§0-§8 是针对「修复前」代码的根因分析（保留作为证据链）；
> **§9 是本次已落地的修复记录**（2026-09-29 ，含构建与验证方式）。
> 实测补充的三条线索已纳入 §9 并用来定位根因：插件每次重进都变回关闭；
> 毛玻璃下圆角变成「半透明尖锐直角」且只有那个小角响应不透明度滑杆；半透明模式完全无效。

**一句话结论：不是「材质没写」，而是**
**① 插件根本不会被触发（A1/A2/A3）；② 触发后「亚克力」和「半透明」在主题层被压成同一个状态，半透明必然变成全透明（B1/B2/B4）；**
**③ 剩下真正依赖系统的亚克力路径有两个静默失败点，且没有任何日志可查（C1/C2）。**
**插件 zip 本身格式正确、确实被成功加载（§1.3），本次不是「zip 损坏」问题。**

### 2.2 三个断点

- **断点 1（A1/A2/A3）**：唯一的触发路径 `on_server_started`，要求「插件已启用」+「该服务器本进程内首次启动」+「日志出现过 `Done (`」三者同时成立。叠加后用户几乎不可能稳定看到效果。
- **断点 2（B1/B2）**：`BgStyle` 三态在 `apply_bg` 出口被压成 `plugin_bg_active: bool`，主题层再也分不清「亚克力」和「半透明」；`theme::apply` 的 `bg_enabled` 分支只认 `cfg.bg_image`，与插件无关，事实上走不到。
- **断点 3（C1/C2）**：`apply_acrylic` 是「尽力而为、静默失败」的实现，失败时不回滚透明状态、不报错、不降级。

## 3. 根因 A：插件触发链（为什么脚本从不生效）

### A1 启用状态从不落盘 —— 重启即回到禁用（必现）

`PluginManager.states` 在 `set_enabled`/`unload`/`load_zip` 内被更新
（`plugins.rs:273, 298, 314, 317, 327`），但 `main.rs` **从未把它写回 `self.cfg.plugin_states`，
也没有在切换后 `save_config()`**。全仓库对 `plugin_states` 的引用只有 4 处，全是「读」：

- `config.rs:127`（字段）、`config.rs:260`（默认空表）
- `main.rs:11883`、`main.rs:11907`、`main.rs:11960`（三处 `cfg.plugin_states.clone()`）

而加载判定是：

```rust
// src/plugins.rs:150-154
let enabled = self
    .manifest_name_of(&zip_path)
    .and_then(|n| self.states.get(&n).copied())
    .unwrap_or(false);          // ← 未登记 == 禁用
```

**后果**：每次启动，`xmst-frosted-glass-demo` 都以 `enabled = false` 加载；
`PluginManager::emit` 里的 `.filter(|i| i.enabled)`（`plugins.rs:341`）把它直接过滤掉，
`on_server_started` **永远不会被调用**。插件 zip 怎么改都没用。

（旁证：`plugin_configs` 有键值而 `plugin_states` 为空 —— 「点过卡片按钮」留下了痕迹，「启用」没有。）

### A2 `server_started` 每个服务器每次运行最多发一次（必现）

```rust
// src/main.rs:5271-5274
if rt.startup_notified && !rt.plugin_start_emitted {
    rt.plugin_start_emitted = true;
    plugin_evts.push(PluginEvt::ServerStarted(srv_name.clone()));
}
```

`plugin_start_emitted` 是 `ServerRuntime` 字段（`main.rs:1139`）：

- 只在 `impl Default for ServerRuntime`（`main.rs:1319`）初始化为 `false`；
- `runtimes` 只在 `App::load`（`main.rs:1883`）和「添加服务器」（`1994`、`12712`）时构造，
  **每次 start/stop 复用同一个 runtime**；
- `start_server`（`main.rs:2023`）复位了 `startup_notified`/`startup_warned`/`started_at`（`2068-2070`），
  **唯独没有复位 `plugin_start_emitted`**。

**后果**：同一服务器在一次程序运行内，第二次及以后启动都不会再发 `server_started`。
用户最自然的操作序列「启用插件 → 重启服务器 → 期待毛玻璃」，恰好永远撞在这个一次性门控上。
（`plugin_start_emitted` 全仓库仅 4 处引用，无任何复位点。）

### A3 缺少「启用/加载」事件，且启动时不恢复效果（设计缺口）

- 宿主事件只有 6 个：`server_started / server_stopped / log_line / player_joined / player_left / backup_done`
  （`main.rs:11912-11943`、`2149`、`2250`、`2505`）。**没有 `on_load` / `on_enabled`。**
- `bg_style` 只被卡片 UI 读（`main.rs:12269-12322`）与写（`main.rs:12495-12500`），
  **没有任何代码在程序启动时按 `bg_style` 重新应用效果**；`plugin_bg_active` 初值恒 `false`（`main.rs:1777`）。
- 卡片「配置」区的背景按钮不检查 `enabled`（`main.rs:12296-12310` 无条件渲染），
  于是「插件禁用但按钮能点」也成立，进一步混淆因果。

## 4. 根因 B：材质层（为什么半透明 = 全透明、毛玻璃会「没有底」）

### B1 `plugin_bg_active: bool` 把「亚克力」和「半透明」合并了（必现，用户当前命中的就是这条）

```rust
// src/main.rs:10915-10925
let win_r = theme::apply(
    ctx, &self.theme_cur, ...,
    self.cfg.bg_alpha,        // 壁纸透明度（与插件无关）
    bg_enabled,               // = !cfg.bg_image.is_empty() && bg_tex.is_some()
    self.plugin_bg_active,    // 被当作 acrylic 形参
);
```

```rust
// src/theme.rs:189-195
let panel_alpha = if acrylic {
    0                                   // ← 亚克力：真透明（让 DWM 模糊透出）
} else if bg_enabled {
    ((1.0 - bg_alpha.clamp(0.0, 1.0)) * 255.0) as u8   // ← 只有配了壁纸才可能走到
} else {
    255                                 // ← 默认不透明
};
```

`apply_bg` 中 **`Translucent` 与 `Acrylic` 都把 `plugin_bg_active` 置 true**
（`main.rs:12013-12032`），主题层只看这一个 bool。因此：

- 点「半透明」→ `plugin_bg_active = true` → `panel_alpha = 0` → **中间内容区完全透明，而不是半透明**；
  同时 `clear_color = [0,0,0,0]`（`main.rs:4994-5000`）。
- 由于左侧导航/顶栏都显式指定了不透明 Frame（见 B3），最终观感是：
  **深色外框照旧，中间内容区直接透出桌面，没有压暗蒙层、没有模糊** —— 即用户描述的「半透明不生效」。
- 用户配置里 `bg_style = "translucent"`（`dist\data\xmst_config.json:161`），**命中的正是这个状态**。

### B2 半透明分支用的不是插件的暗度，且依赖壁纸开关

半透明浓度取自 `cfg.bg_alpha`（设置页「界面 → 背景图透明度」，本机 = 0.6），且必须先满足
`bg_enabled`（`main.rs:10914`：配了 `cfg.bg_image` 且纹理加载成功）。
插件的 `bg_alpha`（`plugin_configs[name].bg_alpha`）只被 `apply_bg` 用于 **Acrylic 的 DWM tint**
（`main.rs:11992-12004`），**与半透明无关**。
卡片里那句「透明度仅对毛玻璃生效」（`main.rs:12352-12356`）既是现状描述，也是 B1/B2 的自我暴露：
**半透明模式根本没有自己的不透明度参数。**

### B3 （已澄清）「结构性面板保持不透明」的注释是错的，但现网靠调用点兜住了

`src/theme.rs:197-204` 的注释与实现：

```rust
// Structural panels (SidePanel / TopBottomPanel / Window / menu) use an opaque
// window_fill ...
v.panel_fill = bg_fill;                       // 半透明/透明
v.window_fill = Color32::from_rgb(c.panel.r(), c.panel.g(), c.panel.b());   // 不透明
```

egui 0.29.1 的事实相反（`egui-0.29.1/src/containers/frame.rs:91-105`，调用点 `panel.rs:280 / 721 / 1111`）：

| 控件 | 默认填充 |
|---|---|
| `SidePanel::default()` | **`panel_fill`** |
| `TopBottomPanel::default()` | **`panel_fill`** |
| `CentralPanel::default()` | **`panel_fill`** |
| `Window` | `window_fill()`（`window.rs:439`） |
| menu / popup | `window_fill()`（`menu.rs:196/392`、`popup.rs:211/408`） |
| `CollapsingHeader` | 无 Frame，走 widget 状态色（`collapsing_header.rs:561-578`） |

**但本项目在全部 6 处面板构造点都显式给了不透明 Frame**（已逐一核对）：

- `main.rs:5422-5427` 顶栏 `TopBottomPanel::top("top")` → `Frame::none().fill(Color32::from_rgb(22,25,32))`
- `main.rs:5620-5623` 左导航 `SidePanel::left("nav")` → `.fill(...window_fill)`
- `main.rs:6179-6180`、`9502-9505`、`11241-11244`、`13384-13387` → 同样显式 `window_fill`

所有中央面板（`main.rs:6042, 6427, 9529, 11272, 12085, 13244`）都用 `panel_fill`（亚克力下达 alpha 0）。
**结论修正**：现网行为＝「外框深色不透明 + 中央内容区透明露出模糊」，符合设计意图；
`theme.rs` 的注释是错误认知，属于**维护风险**（任何新增面板若忘记 `.frame(...)`，会自动继承透明 `panel_fill`），不是当前 bug。
这条注释很可能就是此前多轮「只角落生效」误判的思想来源。

### B4 亚克力失败被静默吞掉，UI 却宣告成功

```rust
// src/main.rs:12013-12023
plugins::BgStyle::Acrylic => {
    let hwnd = main_hwnd();
    if !hwnd.is_null() {
        ...
        plugins::apply_acrylic(hwnd as isize, true, alpha);   // ← 返回值丢弃
    }
    self.plugin_bg_active = true;                             // ← 无条件切到「透明」
    self.set_toast("毛玻璃（亚克力）背景已开启（实验性，依赖系统合成支持）".to_string());
}
```

`apply_acrylic` 明确会返回 false（`plugins.rs:544-597`）：`LoadLibraryW` 失败、
`GetProcAddress` 取不到 `SetWindowCompositionAttribute`、或 `swca(...) == 0`。
三种失败都不回滚 `plugin_bg_active`、不提示、不降级 —— 于是「亚克力没生效」时用户看到的
是**中央区域直接裸透桌面**，而不是「保持默认背景 + 一条错误提示」。

`main_hwnd()`（`main.rs:4934-4960`）按「同进程 + 标题包含 `XMST`」枚举顶层窗口。
当前标题 `XMST - 修暝的服务器工具`（`main.rs:4809`）满足条件，**这条不是本次根因**；
但它属于按标题字符串猜窗口的脆弱实现，改动标题或多窗口时可能返回 null 并静默跳过亚克力。

## 5. 根因 C：亚克力/透明合成的真机前提（必须运行时验证）

### C1 暗度参数的语义陷阱（本机配置已命中）

```rust
// src/plugins.rs:579-589
let mut accent = AccentPolicy {
    accent_state: if enable { ACCENT_ENABLE_ACRYLICBLURBEHIND } else { ACCENT_DISABLED },
    accent_flags: 0,
    gradient_color: if enable { (alpha as u32) << 24 } else { 0 },   // AABBGGRR，RGB 恒为 0
    animation_id: 0,
};
```

- RGB 恒为 0 → 只可能得到**纯黑着色的模糊**（没有浅色/白色亚克力）。
- `gradient_color` 的高字节同时承担两件事：**着色浓度**与**模糊是否生效**。
  该字段的语义来自逆向（`twinui.pdb`）：acrylic 层的背景**就是** `GradientColor`（AABBGGRR），
  alpha 即着色不透明度（[swcadef.h](https://cdn.jsdelivr.net/npm/windows-swca@2.0.2/src/swcadef.h)）。
- **alpha = 0 会破坏效果**：`window-vibrancy`（Tauri/winit 生态主流实现）显式把 0 改成 1，
  注释原文 "acrylic doesn't like to have 0 alpha"
  （[windows.rs](https://docs.rs/window-vibrancy/0.8.1/src/window_vibrancy/windows.rs.html)）。
  本机 **`plugin_bg_alpha = 0.0`**（`dist\data\xmst_config.json:165`）正是这个高风险取值：
  当前这次请求恰好被插件自己的 `bg_alpha = "0.47"`（≈120）覆盖，属**潜在雷**；
  一旦插件配置里没有 `bg_alpha` 键，`main.rs:12016-12018` 就回落到全局 0.0 → **必然不模糊**。
- 反向的坑也有：alpha 接近 255 会变成「几乎实色的遮罩」，看起来就像「只有纯色没有模糊」
  （Terminal 的同类报告：acrylic 打开后变成实色，[terminal#18189](https://github.com/microsoft/terminal/issues/18189)）。
  但 alpha=204（0.8）本身**仍能看见模糊**，所以「完全看不出模糊」不能用 204 解释——
  主因还是模糊本身没起来（见 C2/C4）。社区经验区间：可见模糊约在 `0x40..0x99`，不要 0、不要 ≥0xC0。
- 建议：暗度与「是否启用模糊」解耦（启用时 `alpha.max(1)`），滑杆有效区间收到例如 0.25..=0.60。

### C2 透明底座的两个静默前提（依赖源码已核对）

1. `main.rs:4815 .with_transparent(true)`
   → `egui-winit-0.29.1 lib.rs:1610-1612` `.with_transparent(true)`
   → **winit 0.30.13** `platform_impl/windows/window.rs:1228-1247`：
   `DwmEnableBlurBehindWindow(hwnd, { DWM_BB_ENABLE | DWM_BB_BLURREGION, fEnable: TRUE, hRgnBlur: CreateRectRgn(0,0,-1,-1) })`
   —— 用「空模糊区域」让客户区真正透明。
   **不会引入 `WS_EX_LAYERED`**：`WindowFlags::TRANSPARENT` 只被写入、从不参与样式计算
   （`window_state.rs:256-313` 无该分支；唯一 `WS_EX_LAYERED` 是 `IGNORE_CURSOR_EVENT` 时，`window_state.rs:300-302`）。
   → 项目此处的做法是对的。
2. `eframe-0.29.1 glow_integration.rs:922-926` `.with_transparency(viewport.transparent)`
   → glutin 0.32.3 WGL ARB 路径（`api/wgl/config.rs:245-248`）请求 `WGL_TRANSPARENT_ARB=1`，
   且 `ALPHA_BITS_ARB=8`；`alpha_size: 8` 本就是 glutin 默认值（`config.rs:331-341`），
   eframe 从未调用 `with_alpha_size`（`with_transparency` 只置 flag，`config.rs:211-214`）。
   → egui_glow 的混合也正确保留目标 alpha（`egui_glow-0.29.1 painter.rs:317-330`），
   着色器不强制 alpha=1；eframe 把 `clear_color` 原样传给 `gl.clear_color`（`painter.rs:761-767`）。
   → **「alpha=0 的中央面板 → DWM 透出」这条链路在代码上成立。**

**但仍有两个无法静态确认的失败点，且都没有日志：**

- 若运行时落到 **WGL 传统路径**（`api/wgl/config.rs:50-152`：`ChoosePixelFormat` + `PIXELFORMATDESCRIPTOR`），
  该路径**完全丢弃透明语义**（`dwFlags` 只有 `PFD_SUPPORT_OPENGL|PFD_DOUBLEBUFFER|PFD_DRAW_TO_WINDOW`，
  不含 `PFD_SUPPORT_COMPOSITION`；`template.transparency` 无处使用）→ 窗口不可 alpha 合成，
  中央面板再怎么 alpha=0 也不会透出。
- 想靠日志发现这一点也做不到：
  - 本仓库**没有初始化任何 logger**（无 `env_logger`、无 `log::*`），
    winit 的 `warn!("Setting transparent window is failed...")` 与 eframe 的
    `log::error!("Cannot create transparent window: the GL config does not support it")` **全被丢弃**；
  - 而且 eframe 那处 error 分支对根窗口是**死代码**：它位于
    `glow_integration.rs:1095-1108` 的 `else`（`viewport.window` 为 `None`）分支内，
    而根窗口在 `:1038` 就已插入 `Some(...)`；
  - glutin-winit 里「不支持透明就降级 `with_transparent(false)`」的保护
    （`glutin-winit-0.5.0 lib.rs:199-202`）只在 `finalize_window` 路径生效，WGL 根窗口不走它。
- 补充：winit 的**运行时** `Window::set_transparent` 在 0.30.13 的 Windows 后端只是置 flag、无任何视觉作用
  （`window.rs:121-130`；文档 `src/window.rs:929-934` 自述仅为 hint）。
  因此项目注释里「运行时 Transparent 会加 `WS_EX_LAYERED` 破坏 DWM 合成」
  （`main.rs:12011`、`plugins.rs:540-542`）**机制描述是错的**，
  但由此得出的结论「只能在创建期设置」**仍然正确**（原因不同：运行时它根本不改样式）。

**关键推论（本次最重要的技术判断）**：
`DwmEnableBlurBehindWindow` 自 Windows 8 起就**不再产生模糊**，只保证「窗口 alpha 被尊重」
（MS 文档原文："Beginning with Windows 8, calling this function doesn't result in the blur effect…"，
[DwmEnableBlurBehindWindow](https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/nf-dwmapi-dwmenableblurbehindwindow)）。
winit 走的正是这条「空区域 blur-behind」，且它把 `DwmExtendFrameIntoClientArea` 注释掉了。
所以在本机（Win10 19045）上：

> **透明（alpha 合成）来自 winit，模糊只能来自 `SetWindowCompositionAttribute` 的 AccentPolicy。**
> AccentPolicy 一旦没生效/被抑制，中央区域就是「透明但无模糊」——也就是「材质没做出来」。

而 Win11 的替代路线（`DWMWA_SYSTEMBACKDROP_TYPE`）**要求 build ≥ 22621**，在本机不可用；
`DWMWA_REDIRECTIONBITMAP_ALPHA` 更是 24H2（26100）才引入
（[DWMWINDOWATTRIBUTE](https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/ne-dwmapi-dwmwindowattribute)）。
**即：这台机器上「旧路不能丢、新路用不了」，只能把 AccentPolicy 这条路走通或改用 DComp。**

### C3 真机确认清单（建议照做，一次定位）

1. **窗口是否真的可 alpha 合成**：临时把 `v.panel_fill` 固定成「半透明深色」
   （如 `Color32::from_rgba_unmultiplied(22,22,26,140)`），不启用任何插件效果，看窗口内能否看见桌面被压暗。
   - 能看见 → alpha 合成正常，问题在亚克力 Accent 或暗度（C1）。
   - 看不见（黑/实色）→ 透明底座没建立（C2 第一种），与插件无关。
2. **亚克力调用是否成功**：给 `apply_bg` 临时加一行，把 `apply_acrylic(...)` 的返回值写进
   `data\crash.log` 或插件日志（UI 已有「插件日志」折叠区，`main.rs:12463-12483`）。
3. 同时记录 `GetWindowLongW(hwnd, GWL_EXSTYLE) & WS_EX_LAYERED`、`DwmIsCompositionEnabled`、
   `glGetIntegerv(GL_ALPHA_BITS)`（或 `DescribePixelFormat`），把三个断言一次打全。
4. 用 `gradient_color = 0x01000000` 与 `0x78000000` 各试一次，验证 C1 中「alpha=0 ≈ 不模糊」在本机是否成立。
5. 若需要 eframe 的调试日志：`RUST_LOG=debug` **必须配合 logger 初始化**才有输出——
   当前程序没有，这一步需要先按 §6 P2-9 加落盘日志。

### C4 系统级抑制条件：本机已排除一项，其余待用户确认

Acrylic 除代码外还会被系统策略整体关闭：**「透明效果」关闭、节电模式/Energy Saver、
高对比度主题、远程桌面（RDP）、低端硬件**（MS 文档：
"Acrylic effects are automatically disabled when a device enters Battery Saver…
Users can disable acrylic effects for all apps by turning off Transparency effects"，
[Acrylic material](https://learn.microsoft.com/en-us/windows/apps/design/style/acrylic)；
Terminal 维护者的排查清单同样是 battery / RDP / transparency，
[terminal#18189](https://github.com/microsoft/terminal/issues/18189#issuecomment-2479500965)）。

本机已直接读注册表核对：

| 检查项 | 值 | 结论 |
|---|---|---|
| `HKCU\...\Themes\Personalize\EnableTransparency` | **1** | 透明效果**已开**，未抑制 |
| `HKCU\SOFTWARE\Microsoft\Windows\DWM\Composition` | **1** | DWM 合成**已启用** |
| `ColorPrevalence` | 0 | 无「标题栏/开始菜单强调色」干扰 |
| 是否处于节电模式 / RDP 会话 | **未能查询**（沙箱拒绝 `powercfg` 与 `Win32_Battery`） | **需要用户确认**：`设置 → 系统 → 电源和睡眠 → 节电模式` 是否开启；是否为远程桌面会话 |

结论：C1/C2 之外，「透明效果被关」这条最常见的原因在本机**不成立**；
但「节电模式 / 远程桌面」这两条仍未排除，若用户确实在笔记本电池模式下测试，
亚克力会被系统直接抑制，表现为「完全没模糊」——这与代码层缺陷叠加，会让人误判为插件无效。

## 6. 修复建议（按优先级）

### P0 —— 让插件真的能触发

1. **持久化启用状态**（`main.rs:12441-12450`，以及 `unload`/`reload_all` 处）：
   切换后执行 `self.cfg.plugin_states = pm.states.clone(); self.save_config();`
2. **复位一次性门控**：`start_server`（`main.rs:2068` 附近）增加 `rt.plugin_start_emitted = false;`，
   使每次启动都能重新触发 `server_started`（自动重启/崩溃重启路径同样处理）。
3. **新增 `plugin_enabled` 事件**（或 `set_enabled(true)` 后立即 emit 一次），
   让 demo 插件在「启用」瞬间就能应用背景效果；宿主侧同时支持「启动时按 `plugin_configs[*].bg_style` 恢复效果」。
4. demo 插件 `events` 扩为 `["server_started","plugin_enabled"]`，两个钩子共用同一段应用逻辑。

### P1 —— 把三种模式分开

5. `theme::apply` 的 `acrylic: bool` 换成 `bg_mode: BgMode`：
   - `Opaque` → `panel_alpha = 255`（现状默认）；
   - `Translucent(p)` → `panel_alpha = (p * 255)`，颜色取 `c.bg` —— **真正的半透明蒙层，不再依赖壁纸开关**；
   - `Acrylic(p)` → `panel_alpha = 0`，暗度只交给 DWM tint。
   `main.rs:10915-10925` 与 `apply_bg` 相应改造（`plugin_bg_active: bool` → `plugin_bg_mode: BgMode`）。
6. 修掉 `theme.rs:197-204` 的错误注释；若「导航/顶栏保持不透明」是产品要求，
   则继续在调用点显式 `.frame(...)`（现状），并在注释里写明「egui 默认走 `panel_fill`，必须显式覆盖」，
   避免下一个维护者再次误判。

### P2 —— 让亚克力可诊断、可降级

7. `apply_acrylic` 返回值必须被使用：失败 → 不切 `plugin_bg_active`（保持默认背景）+
   明确提示「系统不支持亚克力」+ 回退到 P1 的半透明蒙层。
8. 暗度与模糊解耦（`alpha.max(1)`），`gradient_color` 的 RGB 由固定 0 改为可配（或至少支持浅色亚克力）；
   全局 `plugin_bg_alpha` 默认值不要落在会让模糊消失的 0.0。
9. 增加最小可观测性：把 `apply_acrylic` 返回值、`WS_EX_LAYERED`、`DwmIsCompositionEnabled`、
   `GL_ALPHA_BITS` 写入 `data\crash.log` 或插件日志（两条落盘通道项目已有，无需引入 `log`/`env_logger`）。
10. **Win10 继续用 state 4，但把 tint alpha 夹到可见模糊区间**（约 `0x40..=0x99`，永不 0、避免 ≥0xC0），
    并在调用后校验返回值（社区实现会在 0 时强制改成 1，
    [window-vibrancy](https://docs.rs/window-vibrancy/0.8.1/src/window_vibrancy/windows.rs.html)）。
11. **中期：Win11（build ≥ 22621）改走 `DwmSetWindowAttribute(DWMWA_SYSTEMBACKDROP_TYPE, DWMSBT_TRANSIENTWINDOW)`**，
    必要时先 `DwmExtendFrameIntoClientArea(hwnd, {-1,-1,-1,-1})`
    （backdrop 只画在「DWM 边框扩展到客户区」的范围），并与 Win10 Accent 路径二选一，
    避免「同一份代码在 Win10 能看、Win11 全失效」。
    注意该属性在 Win10 上只会静默失败/不生效，不能无条件调用。
12. **若要 100% 可靠**：对 GPU 合成内容（OpenGL swapchain），社区结论是
    `DCompositionCreateBackdropBrush` 垫在 swapchain 视觉之下才稳；
    或改用 Windows App SDK 的 `DesktopAcrylicController`/`MicaController`
    （[system backdrops](https://learn.microsoft.com/en-us/windows/apps/develop/ui/system-backdrops)）。
    这是大改，除非「毛玻璃」是核心卖点，否则建议先做 1-11。
13. **加一条自检提示**：启动/应用时读 `EnableTransparency`、检测节电模式与 RDP 会话，
    命中时直接告诉用户「系统策略已关闭透明效果，亚克力不可用」，避免用户误判为工具 bug。

### P3 ——（附带发现 D1）让本地 eframe 补丁真正生效

14. `F:\XMST\vendor\eframe-0.29.1` 里的「托盘隐藏时不再 Poll 空转」补丁**没有被编译**。

## 10. 真机实测：本机所有系统级透明机制均失效 → 改为桌面捕获式背景

### 10.1 实测环境

| 项 | 值 |
|---|---|
| 系统 | Windows 10 Pro 22H2，build 19045.6466 |
| 显示适配器 | NVIDIA GeForce GTX 1060 3GB（驱动 32.0.15.8253）+ 多个虚拟显示适配器（**GameViewer / Parsec / AskLink SDR** → 为远程/虚拟显示环境） |
| 偏好 | `EnableTransparency=1`、`DWM\Composition=1`（系统未关闭透明效果） |
| 渲染栈 | eframe 0.29.1 + glow(OpenGL) + glutin 0.32.3(WGL) + winit 0.30.13 |

### 10.2 逐项实测结论（全部为「调用成功但像素无任何变化」）

用外部探针在真实运行窗口上取样，背景为亮色桌面（实测参考值 `(245,249,250)` 与 `(202,222,234)`）：

| 机制 | 调用结果 | 像素结果 | 判定 |
|---|---|---|---|
| 逐像素窗口 alpha（winit `with_transparent(true)` → `DwmEnableBlurBehindWindow` 空区域） | 创建成功 | 中央 alpha=0 处为 **纯黑 (0,0,0)**，桌面完全不可见 | ✗ 不被合成 |
| `DwmEnableBlurBehindWindow`（`hRgnBlur=NULL` 整窗 / 全窗矩形区域） | `hr=0x0` | 同上，仍为纯黑 | ✗ |
| `DwmExtendFrameIntoClientArea(-1)` | `hr=0x0` | 同上 | ✗ |
| `SetWindowCompositionAttribute` 亚克力（`ACCENT_ENABLE_ACRYLICBLURBEHIND`） | 返回 TRUE（`accent_ok=true`） | 看不到模糊/着色 | ✗ |
| `WS_EX_LAYERED` + `SetLayeredWindowAttributes(LWA_ALPHA)`（外部强制施加，alpha=80/200） | 返回 TRUE，`WS_EX_LAYERED` 已写入 | `(22,22,26)` → `(21,21,24)`，**几乎无变化** | ✗（分层 alpha 只作用于 GDI 重定向表面，GPU 呈现内容不受影响） |
| 半透明覆盖层（面板 alpha=13，即 5%） | — | `(1,1,2)`：是**叠在黑底上**而不是叠在 `(202,222,234)` 桌面上 | ✗ 证明窗口 alpha 未被合成 |

**根因**：OpenGL 的呈现路径在现代驱动 / 远程-虚拟显示会话下是**不透明**的（DXGI flip 模型 / 硬件合成旁路），
DWM 拿到的是一张不透明位图，因此「窗口透明」这类效果在该栈上**没有任何宿主程序可用的实现方式**
（NVIDIA 控制面板里的「OpenGL GDI compatibility / 优先 GDI 兼容」可切换成经典 blt 路径，
是唯一可能恢复逐像素 alpha 的用户侧开关；DirectComposition 重写渲染呈现层是另一条重工程路线）。

### 10.3 已落地的替代实现：桌面捕获式背景（`src/backdrop.rs`）

既然「让窗口透明」在本机不可行，就**把窗口背后的桌面抓进窗口当背景**，效果等价且与环境无关：

1. `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` —— 抓屏时排除本窗口（同时避免自我递归，
   并让用户在**其它窗口**里正常截屏时不会被本窗口的历史帧污染）；
2. GDI `BitBlt` 抓取窗口所在屏幕区域 → `GetDIBits` 读回 BGRA → **盒式降采样**
   （半透明 4×，毛玻璃/亚克力 12×；降采样 + 线性放大 = 廉价模糊）；
3. 作为 egui 纹理画在 `LayerId::background()`，面板按 `plugin_bg_opacity` 叠在其上；
4. 80ms 节流抓取；**窗口几何变化时强制立即重抓**（拖动/缩放不滞后）；
5. 退出效果（切回默认背景）时撤销抓屏排除。

实测验证（`data\bg_debug.log`）：

```
[00:58:44] ... | backdrop mean=(0,0,0) samples=[] captures=0 tex=0x0        ← 启动首帧：尚未抓取
[00:58:45] ... | backdrop mean=(42,43,45) samples=[27,27,28 21,21,23 21,21,23 21,21,23] captures=1 tex=369x238
```

**自捕获判别测试**：把本工具主题临时改成纯白（`custom_bg=[240,240,240]`）后重跑，
捕获样本仍是 `(27,27,28)/(21,21,23)`（桌面内容）而**不是** `≈240`
→ 证明抓到的是窗口背后的真实桌面，`WDA_EXCLUDEFROMCAPTURE` 生效、没有自我递归。

### 10.4 材质与可读性（实测反馈后补做）

第一版捕获方案只把底图铺在 background 层、面板仍按滑杆做半透明填充，实际效果是
「整窗一块模糊玻璃、按钮和文字几乎看不见」——因为深色主题的**浅色文字**被放到了
**明亮桌面**上（浅字 + 亮底 ≈ 对比度 2:1）。

修正后的材质模型：

1. **材质 = 捕获底图 + 主题底色按滑杆不透明度着色**，整体画在 `LayerId::background()`
   （`main.rs::paint_bg`）。这层着色既是「玻璃的颜色」，也是下面第 3 步算对比度的基准。
2. **面板填充 alpha = 0**（材质模式下不再叠第二层），侧栏/顶栏/弹窗改用
   `window_fill` 的「材质近不透明版」（alpha 236），保证与内容区同色系。
3. **前景自动对比**：`main.rs::tick_theme` 用「材质合成色 = 主题底色 × 不透明度 +
   捕获均值 × (1−不透明度)」调用 `theme::auto_contrast`，由它决定用深色还是浅色文字、
   控件底色、描边（深色材质→浅字，明亮材质→深字），从根本上消除「浅字 + 亮底」。
4. 材质模式下不再叠加用户壁纸（否则壁纸会盖住材质）。

调色参考：不透明度 0.70 时，纯白桌面 → 材质 luma ≈ 89（浅字对比度 ≈ 5:1，舒适）；
不透明度 0.55 → ≈ 122（临界，仍可读但偏灰）。

### 10.5 反馈修复（材质盖住整个 UI）

用户复测反馈：「底色透明了，但按钮/UI 完全看不见」。用**内置自测截图**（从自己的
帧缓冲取图，不受抓屏排除影响）取到实证：

| 模式 | 帧缓冲最大亮度 | 亮度>120 的像素 | 结论 |
|---|---|---|---|
| 默认 | 238 | 619 | UI 正常 |
| 半透明 | 68 | **0** | **UI 完全没画出来** |
| 毛玻璃 | 75 | **0** | 同上 |

**根因**：egui 的 `CentralPanel` 内容本身就画在 `LayerId::background()` 这一层
（`egui-0.29.1/src/context.rs:538-548` 注册 background area），而同一层内按插入顺序绘制。
我的材质是在 **`update()` 帧末**追加到该层的 → 材质盖在中央内容之上。
（这也是历史反馈「背景图盖住按钮」的同源问题，当时只靠把侧栏改成不透明绕开了。）

**修复**：把 `paint_bg(ctx)` 从帧末移到 **`tick_theme` 之后、任何面板之前**调用
（`main.rs::update` 开头），材质/壁纸因此永远在 UI 之下。修复后实测：
半透明 `max=238 / >120: 742`、毛玻璃 `max=238 / >120: 752` —— UI 全部回来了。

同时新增 **F12 内置截图**（存 `data\screenshot_<时间>.bmp`）：效果开启时窗口被
`WDA_EXCLUDEFROMCAPTURE` 排除，外部截屏/录屏/PrintWindow 都拍不到本窗口，
内置截图是唯一可靠的取图方式（也为后续排障留了手段）。截图用自写 BMP 头，
避免为诊断功能链入 PNG 编码器（实测会让 exe 从 15.2MB 涨到 18.7MB）。

### 10.7 三种模式的观感区分 + 「低不透明度偏白」的解释

**① 毛玻璃 / 亚克力原本看不出区别**：本机 DWM accent 完全不可用（§10.2），
两者此前在材质阶段又都用同一档模糊（降采样 12×），于是唯一的差别（DWM 的
「模糊」vs「模糊+噪点」）根本没被画出来。现在按模式分别定制材质：

| 模式 | 降采样 | 附加效果 | 语义 |
|---|---|---|---|
| 半透明 | 3× | 无 | 几乎原样的桌面（轻微平滑） |
| 毛玻璃 | 9× | 无 | 高斯模糊感 |
| 亚克力 | 20× | **噪点层**（96×96 重复寻址纹理，alpha 16） | 模糊 + 噪点，与 Windows 亚克力的「blur + noise」一致 |

真机实测（帧缓冲中央区域相邻像素差，数值越大细节越多）：

| 模式 | 中频细节(±2px) | 高频细节(±1px) |
|---|---|---|
| 半透明 | 1.33 | 1.04 |
| 毛玻璃 | 1.15 | 0.80 |
| 亚克力 | **6.31** | **6.31** |

亚克力的高频能量显著抬升 = 噪点层在工作；半透明/毛玻璃的中频细节差 = 模糊档位不同。

**② 「不透明度调低后背景偏白」**：两部分原因，其中一半是刻意适配：

1. **物理原因**：材质 = `主题底色 × 浓度 + 桌面底图 × (1 − 浓度)`。浓度越低，桌面占比越高；
   若桌面本身是明亮的（浏览器白底），材质自然发白。这是效果本身，不是 bug。
2. **刻意适配**：材质变亮后，若仍用深色主题的浅色文字，就会出现「浅字 + 亮底」看不清
   （§10.4 的老问题）。因此 `theme::auto_contrast` 会在材质 luma > 140 时**整体切到浅色界面**
   （浅底 + 深字），连标题栏/侧栏也一起变浅 —— 这就是你看到的「界面偏白」。
3. **现在可自行选择**：插件页新增复选框「**界面配色跟随材质明暗**」（默认开）。
   关闭后界面固定用当前主题配色（保持深色观感），此时材质浓度会被自动抬到 **0.60 下限**，
   避免明亮桌面上变回「浅字 + 亮底」不可读 —— 即「想要深色 UI」与「想要极低浓度」
   二者不可兼得，工具按可读性优先做了取舍。

### 10.9 ：对标 TranslucentTB、文字可读性、拖拽性能

**① TranslucentTB 的实现方式（源码级核对，分支 release@d4636e4）**
- 没有 `blur.cpp`：accent 逻辑在 `TranslucentTB/taskbar/taskbarattributeworker.cpp`，
  另有 `ExplorerHooks/swcadetour.cpp` 在 explorer.exe 内挂 SWCA 钩子。
- Win10 路径**就是** `SetWindowCompositionAttribute(WCA_ACCENT_POLICY)`（我们的尝试 #3）：
  `AccentFlags` 对 acrylic 用 **0**、其余状态（含 blur）用 **2**；`GradientColor` 为 ABGR；
  acrylic 有 `A==0 → A=1` 钳制。**不使用** `DwmEnableBlurBehindWindow`、`DwmSetWindowAttribute`
  或 `DWMWA_SYSTEMBACKDROP_TYPE`（全仓库零命中）。
- 关键差别：它把 accent 下发给 **explorer 的 `Shell_TrayWnd`（跨进程）**——那个窗口**不自己绘制客户区背景**，
  所以 DWM 画的 accent 就是可见背景；而我们的 GL swapchain 把每个像素都画了，accent 被完全遮住。
  它同时 detour explorer 内的 SWCA，防止 explorer 覆盖它的策略。Win11 上它干脆放弃 accent、改换 XAML 画刷。
- 因此**没有可借鉴的第五种机制**：它赢在目标窗口不画背景，不在于对 DWM 做了什么。
  两处可借鉴并已落地：`AccentFlags` 按状态区分（毛玻璃=2、亚克力=0）；静止节流 + 抓屏来源选择（性能）。
- 它的实现在系统「透明效果」关闭时会**静默失效且无任何检测/回退**；我们用 `bg_debug.log` 做得更好。
- **建议用户自测**：打开开始菜单/设置，若系统自身的亚克力也是纯色不透明，则说明本机 DWM 亚克力
  在驱动/虚拟显示栈层面就坏了（NVIDIA 在 Win10 上有过此类已确认回归），**任何宿主代码都改不动**，
  此时「桌面捕获式材质」就是正确答案。

**② 文字可读性（按 Fluent/WinUI/WCAG 结论落地）**
研究结论：**这是不透明度/方差问题，不是配色问题**。微软自家 shell 的做法是「材质之上铺一层近不透明内容层」
（Mica 本身不透明，内容用 `LayerFillColorDefaultBrush`）；WinUI 亚克力配方里有一层
"exclusion blend … to ensure contrast and legibility"；Windows Terminal 默认 `useAcrylic=false`、
opacity 100，靠**不透明度**而非模糊解决可读性；微软还明确不建议在亚克力上放强调色文字。
本次落地三件事：
1. **内容衬底**（新滑杆，默认 0.25）：内容面板不再是全透明，而是主题底色的半透明衬底
   （即 WinUI 的 content layer 思路），桌面材质仍可见。
2. **更强的对比**：材质模式下的自动配色改用近黑/近白极值，控件底色按 `shade(材质, ±Δ)` 推导，
   且判定用的合成色**包含衬底**。
3. **全局 1 物理像素文字描边**（地图标注的经典做法）：给 ≤16pt 的文字复制 4 份偏移 1px、
   明暗相反的颜色垫在下面。该做法合规（WCAG 2.2 SC 1.4.3 Note 5：贴住笔画的**窄**边框算作文字本身，
   宽/模糊光晕才算背景）。
   实现方式：`[patch.crates-io] eframe = { path = "vendor/eframe-0.29.1" }` + 在
   `glow_integration.rs` 的 `tessellate` 之前展开文字形状 —— **顺带把此前一直没进二进制的
   「托盘隐藏不 Poll 空转」P0 补丁真正接上了**。

**③ 亚克力拖拽掉帧（实测根因 + 修法）**
- 实测：**单次抓屏 17~30 ms**（`StretchBlt` 用 HALFTONE 对 1475×950 源做高质量滤波），
  而 60fps 一帧只有 16.7ms；拖动时又每帧强制重抓 → 必然掉帧。日志里加了 `cap_ms/max` 以便验证。
- 修法（全部已落地）：
  1. `SetStretchBltMode(COLORONCOLOR)` 点采样把整窗缩到小图（快），质量改由**小图上的盒式模糊**
     补回来（74×48 上做 5×5 平均，开销可忽略）→ 稳态降到 ~10 ms；
  2. **拖动/缩放期间冻结底图**（几何变化时不抓，复用上一帧），停止约 140ms 后补抓一次
     → 拖动过程**零抓屏开销**，这是掉帧的根治手段；
  3. 复用 GDI 内存 DC/位图（不再每次新建）；
  4. 静止刷新间隔 80ms → 120ms。

### 10.10 ：底图「永远停在打开时那一帧」的根因（含实证）+ 剩余功能

**① 现象**：反馈「背景永远不会更新，一直维持着刚打开的背景」。

**② 根因（上一轮为修拖拽掉帧而自造的 bug）**：
冻结判据写成 `geom_changed = 底图.last_rect != 当前矩形`，而 `last_rect` **只在真正抓取时更新**，
冻结分支又恰好不抓取 → 一旦几何变化过（例如启动时 ppp 从 1.25 变 1.15 导致窗口尺寸微调），
该判据**永远为真** → 第一分支永远命中 → 底图被永久冻死在首次抓取那一帧。

**③ 修法**：
1. 判据改为「本帧矩形 vs **上一帧**矩形」（是否正在移动）+ 停止后 160ms 的沉降窗口；
2. 冻结结束后由 `update()` 内部的「矩形与上次抓取不同」自动强制补抓一次；
3. **保险丝**：任何情况下冻结不超过 2 秒（同类 bug 在结构上不可能再发生）。

**④ 实证**（脚本移动窗口 + 最大化，观察 `captures` 是否继续增长）：
```
03:52:34 captures=2   （移动前）
03:52:35 captures=3
03:52:38 captures=20  ← 移动 +300/+80 之后仍在持续抓取
03:52:42 captures=40  ← SC_MAXIMIZE 之后；tex 由 369x238 变为 645x352（按新几何重建）
```
→ 几何变化后底图持续刷新、并按新尺寸重建纹理 ✅

**⑤ 顺带修掉的两处配置问题**：
* 内容衬底被 UI 滑杆钳制成 `0.0`（等于没有衬底）→ 复位 0.25；
* 插件 `bg_alpha` 在测试中被拖到 `0.05`（日志 `opacity=0.05` + 明亮桌面 = 界面整体发白，
  与用户上一轮「偏白」的反馈完全吻合）→ 复位 0.70。

### 10.11 ：窗口记忆「巨大化」、拖动实时性、D4 单一真源

**① 默认窗口变得巨大（F1 引入的 bug）**：F1 把 `GetWindowRect` 的**外框物理矩形 / ppp** 当成
`window_size` 存了下来，两个后果：
1. 外框包含不可见的缩放边框（比客户区大一圈）→ 每次重启都变大一点（棘轮效应）；
2. **窗口最大化时外框 = 整个屏幕** → 下次启动直接开出「巨大窗口」（反馈的现象）。
**修法**：尺寸一律取 egui 的**客户区逻辑尺寸** `ctx.screen_rect().size()`（这正是
`ViewportBuilder::with_inner_size` 的语义，重启不再漂移）；**最大化时不记录位置与尺寸**；
还原时用主显示器物理尺寸做上限钳制 + 位置越界校验；并新增设置页「**重置窗口位置与大小**」按钮
（一键回 1180×760 并清空记忆），拖动窗口边缘（无边框窗口四边热区）即可缩放。
实测：窗口外框恢复 1180×760；运行后记忆值 = `window_pos [303,138]`、`window_size [1283,826]`
（= 客户区逻辑尺寸，ppp=1.15 下对应 1475×950 物理，与启动尺寸一致，不再棘轮）。

**② 拖动时底图不实时**：上一轮为了不掉帧改成「拖动期间完全冻结」，代价就是松手才更新。
现在改成**两者兼得**：
1. 拖动中仍以 **~200ms** 间隔继续抓取（单次 10~25ms 摊到多帧，不破坏帧率）；
2. 两次抓取之间用 **UV 偏移** 把上一张底图按窗口位移平移 —— **零成本**地让材质始终"钉"在
   桌面内容上，视觉上连续跟随（不会像完全冻结那样"漂移感"）；
3. 拖动刚结束的那一帧强制立即补抓（`min_interval = 0`）拿回真实内容；
4. 保留 2 秒冻结保险丝。
实测：模拟连续拖动（20 次小步移动）期间 `captures` 由 3 增长到 20 → 拖动过程中确实在刷新。

**③ D4 背景状态单一真源（拿到了现场证据）**：配置里同时存在
`plugin_configs["xmst-frosted-glass-demo"].bg_alpha = "0.32"`（插件配置，启动恢复读它）
与 `plugin_bg_alpha = 0.55`（UI 滑杆写的）→ **用户调过的值重启后会变**（日志实测启动生效值
是那个没人再维护的 0.32）。现在 `apply_bg()` 把材质状态**只写插件配置一处**（唯一真源），
并同步历史字段；实测启动值稳定为配置里的 0.70。

### 10.12 ：亮色看不清、半透明也糊、启动告警、侧栏折叠

**① 亮色模式看不清 / 部分字体（如左栏「仪表盘」）不跟随变色** —— 同一个根因：
`fg()`（前景色统一适配）及其依赖的 `theme_is_light()` 读的是**配置里的 `theme_mode`/`custom_bg`**，
而材质模式下 `theme::auto_contrast` 是按**材质实际明暗**整体翻转深浅的。于是出现
「界面已被材质翻成浅色，但用 `fg()` 画的文字/图标仍按深色主题返回浅灰/浅青」→ 看不清、看起来"不跟随"。
**修法**：`theme_is_light()` 改看**当前生效调色板的正文色**（正文偏暗 ⇒ 浅色界面），
配置主题 / 材质翻转 / 手动浅色三条路径因此统一；左栏导航颜色改为直接取调色板
（选中 = accent，普通 = weak），不再写死浅青/浅灰；`auto_contrast` 同时**适配强调色**
（明亮材质上把为深色底设计的亮青压暗，深色材质上把过暗的强调色提亮）。

**② 「半透明」也糊** —— 旧参数 `ds=4`（4× 降采样）**再叠小图盒式模糊半径 1**，
等效十几像素模糊。半透明的语义应是"桌面原样透出来、只叠一层底色"，故改为
**`ds=2` 且不模糊**：纹理由 369×238 变为 1031×664，实机截图可**直接读清窗口背后桌面的文字**。
代价是单次抓屏 ~10ms → ~31ms（GetDIBits 数据量变大），为此加了**自适应刷新节奏**：
桌面内容在变（画面均值跳 > 6）→ 120ms；内容基本不变 → 逐步放宽到 600ms，静止时不再有 1/4 帧被抓屏占用。

**③ 启动时多出一条「打开警告」** —— 背景恢复时 `apply_bg()` 会弹提示条，本机 DWM 亚克力不可用时
还会追加「已回退另一档 DWM 模糊」，于是每次开机都弹一条像告警的提示。
**修法**：启动恢复与插件脚本（`on_enabled`）触发的应用一律**静默**（`bg_suppress_toast`），
手动切换才提示，措辞改为「本机 DWM 亚克力不可用，已用桌面捕获材质实现同等效果」。

**④ 左栏折叠**：新增配置 `nav_collapsed`；折叠后侧栏 56px、**只显示图标**（居中，点击整行仍可切页），
分组小标题与「保存配置」按钮隐藏；**左下角 ◀/▶ 箭头**为展开/折叠按钮
（`bottom_up` 布局固定在面板底部，不随导航项数量浮动），状态持久化。实机截图确认 ✓

### 10.13 副作用与注意

* 效果开启期间，**XMST 会从截屏/录屏/共享屏幕中消失**（这是抓屏底图不自我递归的前提）。
  已在 `docs\工具缺陷盘点与优化建议_2026-09-30.md` D11 中列为待办：
  增加 `bg_capture_exclusion` 配置开关与 UI 说明。
* 抓屏内容就是「窗口背后的真实画面」，因此若背后是暗色内容，毛玻璃也会偏暗 —— 这是正确行为。
* 拖动窗口时若觉得底图滞后：可把 `CAPTURE_INTERVAL`（`backdrop.rs`）调到 40ms，
  或在拖动开始/结束事件里显式 `update(..., force=true)`。
